    ⚡ 60-Second Cheat Sheet — 10 Core Principles
    • 1. Measure first, optimize second — instrument P99 latency + error rate + saturation before changing anything. Never guess bottlenecks.
    • 2. Stateless services = horizontal scaling — session state → Redis, files → S3. If a service can't be killed and replaced any time, it's not stateless.
    • 3. Idempotency is non-negotiable — every mutating API needs an idempotency key. Retries, network blips, and duplicate webhooks are facts of life.
    • 4. Every external call needs a circuit breaker — one downstream failure should never take down your service. Resilience4j or Hystrix, always.
    • 5. Eventual consistency is acceptable; data loss is not — design write paths for durability first, then relax read consistency where the product allows.
    • 6. Design for failure, not success — network is unreliable, disks fail, services crash. Chaos engineering validates your assumptions.
    • 7. Observability beats monitoring — metrics + structured logs + distributed traces (RED method: Rate, Errors, Duration). Alert on symptoms, not causes.
    • 8. Schema evolution must be backward compatible — add columns, never rename/drop in a single deployment. Blue-green + rolling deploys require this.
    • 9. Caching is a read optimization, not a write one — write-through caching only if you understand the invalidation strategy. Cache invalidation is hard.
    • 10. The 8 Fallacies of Distributed Systems — network is NOT reliable, NOT zero latency, NOT infinite bandwidth, NOT secure, topology DOES change, transport cost IS non-zero.

    HikariCP Pool Sizing Formula
    pool_size = (core_count × 2) + effective_spindle_count
    For a 4-core server with SSD (spindle=1): pool = 9. For 8-core with HDD RAID-5 (spindle=5): pool = 21. Typical range: 10–20 per app instance. Too many connections = context-switch overhead; too few = connection starvation.
    🏗 LLD Quick Reference
    Parking Lot Design (Common LLD Question)
    Entities: ParkingLot → ParkingFloor → ParkingSpot → Ticket → Vehicle → Payment
    Key patterns: Strategy (pricing per vehicle type), Observer (spot availability events), Factory (create vehicle from type string)
    Concurrency trick: ConcurrentHashMap<SpotId, AtomicBoolean> for availability. Use compareAndSet(false, true) for atomic allocation. Never use synchronized on the entire lot.
    // Idiomatic Java — 3 patterns in 15 lines
class ParkingLot {
  private final Map<SpotType, Deque<ParkingSpot>> available = new ConcurrentHashMap<>();

  public Optional<Ticket> park(Vehicle v) {
    return available.getOrDefault(v.spotType(), new ArrayDeque<>())
      .poll()  // thread-safe Deque poll
      .map(spot -> Ticket.create(spot, v, pricingStrategy.calculate(v)));
  }
}
    LRU Cache Design
    Java shortcut (interview acceptable): new LinkedHashMap<>(capacity, 0.75f, true) with removeEldestEntry override.
    Custom O(1) solution: HashMap<Key, DLLNode> + Doubly-Linked List. HashMap gives O(1) lookup; DLL gives O(1) move-to-front and evict-tail.
    Distributed LRU: Redis with maxmemory-policy allkeys-lru. Use TTL for time-based expiry on top.
    🏛 HLD 6-Step Framework
    1. Requirements (5 min): Functional (what it does) + Non-functional (QPS, latency SLA, availability %, consistency needs, data durability). Write them on the board.
    2. Estimation (3 min): QPS (peak = avg × 2-3×), storage per record × records/day × retention days, bandwidth. Anchor on powers of 10.
    3. API Design (3 min): Core REST endpoints. Method, path, key request/response fields. Idempotency key on POST mutations.
    4. Data Model (5 min): Core entities, schema, SQL vs NoSQL justification (SQL: ACID + relations; NoSQL: scale + schema flexibility). Partition key choice.
    5. High-Level Design (15 min): Draw components + data flow. Client → LB → API Gateway → Services → DB + Cache + Queue. Show read path and write path separately.
    6. Deep Dive (15 min): Pick 2-3 hardest problems. Scaling the hot path, consistency trade-offs, failure handling, observability. Show you know the trade-offs.

    Double-Entry Ledger (NEVER single balance column)
    -- WRONG: UPDATE accounts SET balance = balance - 100 WHERE id = ?
-- RIGHT: Insert two ledger rows atomically

CREATE TABLE accounts (
  id UUID PRIMARY KEY,
  currency VARCHAR(3) NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE ledger_entries (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  account_id UUID NOT NULL REFERENCES accounts(id),
  amount NUMERIC(20,4) NOT NULL,  -- positive=credit, negative=debit
  balance_after NUMERIC(20,4),    -- optional: snapshot for fast reads
  transaction_id UUID NOT NULL,
  description TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- Balance query:
SELECT SUM(amount) FROM ledger_entries WHERE account_id = ?;
-- Every payment = 2 rows: debit sender + credit receiver (in same transaction)

    ⭐ STAR Behavioral Framework
    S
    Situation — context in 1-2 sentences. Scale it: "handling ₹10Cr/day", "serving 5M users", "team of 8 engineers".
    T
    Task — what YOU specifically were responsible for. Distinguish your role from the team's role.
    A
    Action — what YOU did. Use "I" not "we". Steps taken, decisions made, alternatives considered and rejected.
    R
    Result — quantified outcome. Latency reduced by X%, cost cut by Y%, team velocity increased by Z%. Always end with numbers or learning.
    Worked Example — Technical Conflict
    S: "Senior architect insisted on Oracle for new payment service. I preferred PostgreSQL + Citus for horizontal scale."
    T: "As tech lead, I had to make the architectural decision for a service projecting ₹500Cr/year volume."
    A: "I ran a 2-week PoC: benchmarked both at 3× peak load, modeled 5-year TCO (Oracle ₹40L/yr vs PG free), documented replication + HA capabilities, presented to CTO with data."
    R: "Chose PostgreSQL. Cut infra cost by 42%. Service has run at 99.97% uptime for 18 months. Senior architect became a PostgreSQL advocate."
    📋 Interview Day Playbook
    1. First 2 minutes: Repeat the question back to confirm scope. "So you want me to design X that handles Y scale with Z constraint — is that right?"
    2. Before designing: Ask about scale (QPS), latency SLA (p99), availability (99.9% vs 99.99%), consistency requirements, read:write ratio.
    3. When stuck: "Let me think through the trade-offs here..." and talk through your reasoning. Never go silent for more than 30 seconds.
    4. On disagreement: "That's an interesting approach. I see it slightly differently because [reason]. What's your thinking?" Never be defensive.
    5. Behavioral answers: Every answer ends with quantified result OR explicit learning ("This taught me that...").
    6. Red flags to avoid: "We never had that problem", "I'd just use AWS for that", "I'd Google it", "My team handled that", "It depends" with no follow-up.
    7. Showing principal-level thinking: Mention cost, mention operational burden, mention the team skills required, mention migration path. Juniors solve the problem; principals solve the problem in context.

    URL Shortener Crashes During IPL Finals
    CDNRedis Hot KeyHorizontal ScalingCache StampedeHikariCP
    Architecture + Java Deep Dive
    Architecture Flow
    Browser → CDN Edge (301 cache) → Load Balancer → App Node (Caffeine L1, 10K entries) → Redis Cluster (L2) → PostgreSQL Read Replica → Primary DB
    Root Cause

    A single short URL trending during IPL = one Redis slot getting 100K req/sec. Redis is single-threaded per slot — the hot key becomes the bottleneck. DB connection pool (HikariCP default: 10) exhausts on cache miss burst.

    Java / Spring Boot Fix
    // L1: Caffeine in-process cache (never hits Redis for top URLs) @Bean CacheManager cacheManager() { return new CaffeineCacheManager("urls") {{ setCaffeine(Caffeine.newBuilder() .maximumSize(10_000).expireAfterWrite(5, MINUTES)); }}; } // L2: Redis — shard hot keys across 10 replicas String redisKey = "url:" + shortCode + ":" + (shortCode.hashCode() % 10); // Reads pick random suffix; writes replicate to all 10
    301 vs 302 Redirect
    Secret: Use 301 (Permanent) for popular stable URLs — browser caches it, zero subsequent requests to origin. Use 302 (Temporary) when you need click analytics. Most candidates say "302 always" and burn origin capacity.
    Interview Trap: "Add more servers" is wrong. More app servers don't help a hot Redis key — they all hit the same Redis slot. Fix the cache tier first.

    02
    WhatsApp Users Receive Duplicate Messages
    IdempotencyAt-Least-OnceKafka RetriesDeduplication
    Architecture + Java Deep Dive
    Why Duplicates Happen

    Kafka guarantees at-least-once delivery. On consumer crash after processing but before offset commit, the message is redelivered. Same with network retries — client resends if ACK not received.

    Architecture Flow
    Client → WebSocket → Message Service → Kafka (at-least-once) → Consumer → Redis Dedup Check → if NEW: persist to Cassandra + push notification → if DUPLICATE: drop silently, return 200 to producer
    Java: Idempotent Consumer
    @KafkaListener(topics = "messages", containerFactory = "factory") public void consume(Message msg, Acknowledgment ack) { String key = msg.getSenderId() + ":" + msg.getClientMsgId(); // SETNX with TTL = idempotent window (24h) Boolean isNew = redis.opsForValue() .setIfAbsent(key, "1", 24, HOURS); if (Boolean.TRUE.equals(isNew)) { messageRepository.save(msg); pushService.notify(msg.getReceiverId(), msg); } ack.acknowledge(); // manual commit AFTER processing }
    Secret: Idempotency key = {senderId}:{clientGeneratedMessageId}. The client generates the ID before sending — this is how WhatsApp, Signal, iMessage all work.
    Interview Trap: Saying "use Kafka exactly-once semantics" without explaining the additional latency cost and that it only helps within the Kafka pipeline, not at the application layer.

    Swiggy Shows Wrong Rider Location
    WebSocketMQTTRedis GEOKafka Streams
    Architecture + Java Deep Dive
    Architecture Flow
    Rider App → MQTT Broker (low-overhead TCP) → Location Processor → Redis GEO (current pos) → Kafka (event log) → WebSocket Server → Customer App (live updates)
    Why MQTT over HTTP

    MQTT is 80% less battery drain than HTTP polling. Persistent TCP connection + 2-byte minimal header. Rider sends location every 2 seconds — over 8-hour shift that's 14,400 updates. HTTP overhead would kill the battery.

    Java: WebSocket Location Push
    @MessageMapping("/rider/location") public void updateLocation(LocationEvent event) { // Store current position in Redis GEO geoOperations.add("riders", new Point(event.getLng(), event.getLat()), event.getRiderId()); // Push to customer via WebSocket String dest = "/topic/order/" + event.getOrderId() + "/location"; template.convertAndSend(dest, event); // Publish to Kafka for analytics/history kafkaTemplate.send("rider-locations", event.getRiderId(), event); }
    Secret: The lag is usually not network — it's the smoothing algorithm. GPS points jump. Apps interpolate between last-known and new position (linear interpolation over 2s). Wrong interpolation = apparent lag.
    Interview Trap: Designing with HTTP polling ("rider calls an endpoint every 2 seconds") — this doesn't scale and destroys mobile battery. WebSocket + MQTT are the right answers.

    Netflix Buffers Right After New Season Drops
    CDNCache WarmingAuto ScalingOpen Connect
    Architecture + Java Deep Dive
    Netflix's Actual Architecture
    User → Netflix CDN Edge (Open Connect Appliance at ISP) → ISP Peering Point → Netflix Regional CDN → Origin [Most users never hit origin — served from ISP CDN]
    Why Buffering Happens at Launch

    On premiere, CDN edge nodes have cold cache — first request for each video chunk must go to origin. Origin gets hammered by millions of simultaneous first requests. Fix: pre-warm the CDN before release by pushing content to edge nodes 24h before premiere.

    Cache Warming Strategy
    // Pre-warming: push popular content to CDN before release @Scheduled(cron = "0 0 2 * * ?") // 2 AM before premiere public void warmCDNEdges() { List<String> upcomingReleases = contentService.getReleasesToday(); upcomingReleases.parallelStream().forEach(contentId -> { // Trigger CDN prefetch API (CloudFront/Akamai-specific) cdnClient.createInvalidationAndPrefetch(contentId); // Also set long Cache-Control headers contentService.setMaxAge(contentId, Duration.ofDays(7)); }); }
    Secret: Netflix uses Predictive Auto-Scaling — they scale up EC2 instances the night before Thursday (their biggest release day) based on ML prediction, not reactive CPU thresholds.
    Interview Trap: Not mentioning CDN at all. Without CDN, no scaling strategy is sufficient — 200M concurrent streams cannot be served from any origin cluster.

    Uber Surge Pricing During Rain
    Kafka StreamsReal-Time AnalyticsGeohashDynamic Pricing
    Architecture + Java Deep Dive
    Architecture Flow
    Driver GPS → Kafka ("driver-locations") → Kafka Streams (window: 5-min, key: geohash6) → Count drivers per geohash → Rider requests per geohash → Surge = riderRequests / availableDrivers → Redis ("surge:{geohash}") → Pricing API
    Java: Kafka Streams Surge Calculator
    KStream<String, LocationEvent> drivers = builder.stream("driver-locations"); // Count available drivers per geohash in 5-min window KTable<Windowed<String>, Long> driverCounts = drivers .filter((k, v) -> v.isAvailable()) .groupBy((k, v) -> GeoHash.encode(v.getLat(), v.getLng(), 6)) .windowedBy(TimeWindows.ofSizeWithNoGrace(ofMinutes(5))) .count(); // Join with rider demand → compute multiplier surgeMultipliers .toStream() .foreach((window, surge) -> redis.opsForValue().set( "surge:" + window.key(), surge, 5, MINUTES));
    Secret: Uber uses Geohash level 6 (~1.2km × 0.6km cells). Level too fine = not enough drivers per cell. Level too coarse = surge doesn't reflect local supply. Geohash 6 is the sweet spot for city-level matching.
    Interview Trap: Using batch processing (run every 5 minutes via scheduler). Stream processing is mandatory — surge needs to update in seconds, not minutes.

    Amazon Cart Shows Old Data
    Cache InvalidationCache-AsideWrite-ThroughTTL Strategy
    Architecture + Java Deep Dive
    Cache Pattern Comparison
    PatternHowStale Risk
    Cache-AsideRead: check cache → miss → DB → cache. Write: DB then evict cacheLow (explicit eviction)
    Write-ThroughWrite: DB + cache simultaneouslyLow (always consistent)
    Write-BehindWrite: cache first → async flush to DBHigh (flush delay)
    Java: Cache-Aside with Spring Cache
    @Cacheable(value = "cart", key = "#userId") public Cart getCart(String userId) { return cartRepository.findByUserId(userId); } @CacheEvict(value = "cart", key = "#userId") @Transactional public void addItem(String userId, CartItem item) { cartRepository.addItem(userId, item); // Cache evicted → next read rebuilds from DB } // Protect against stampede on eviction @CachePut(value = "cart", key = "#userId") @Transactional public Cart updateAndRepopulate(String userId, CartItem item) { Cart updated = cartRepository.updateAndReturn(userId, item); return updated; // immediately re-populates cache }
    Secret: Amazon actually uses eventual consistency intentionally for the cart — showing a slightly stale cart is acceptable for 1-2 seconds. The shopping cart is a "low-stakes" read. Checkout is strict-consistent (hits DB directly, bypasses cache).
    Interview Trap: Saying "set TTL to 0" (no TTL) — this is fine for correctness but dangerous if eviction never happens and cache grows unbounded. Always set a reasonable TTL even with explicit eviction.

    Instagram Notification Storm (Celebrity Posts)
    Fanout-on-WriteFanout-on-ReadKafkaBackpressureHybrid Fanout
    Architecture + Java Deep Dive
    The Celebrity Problem

    Virat Kohli posts → 200M followers. Fanout-on-write = 200M writes to Redis feeds. That takes minutes. Fanout-on-read = every follower reads his timeline on login. Both are wrong alone — hybrid is the answer.

    Hybrid Fanout Architecture
    Post Published → Kafka ("posts") → Fanout Service reads event → IF user.followerCount < 10K (regular): push to each follower's Redis feed → IF user.followerCount ≥ 10K (celebrity): store post only in author's timeline → On client read: merge celebrity posts (pull) + friend posts (push)
    Java: Tiered Fanout
    @KafkaListener(topics = "posts") public void fanout(PostEvent post) { User author = userService.get(post.getAuthorId()); if (author.getFollowerCount() < 10_000) { // Push to all followers' feed lists in Redis List<String> followers = followService.getFollowers(post.getAuthorId()); followers.forEach(followerId -> redisList.leftPush("feed:" + followerId, post.getId())); } // Celebrities: just store post; clients pull on read timelineService.saveToAuthorTimeline(post); }
    Secret: Instagram uses a threshold of ~10,000 followers to switch from push to pull. The actual number is tuned by measuring fanout queue depth vs read latency tradeoff.
    Interview Trap: Designing a single fanout strategy for all users. Celebrity accounts break fanout-on-write. Regular users suffer latency from fanout-on-read. Hybrid is mandatory at scale.

    Payment Deducted But Order Failed
    Saga Pattern2PC vs SagaCompensationTemporalOutbox Pattern
    Architecture + Java Deep Dive
    Why 2PC Fails at Scale

    2-Phase Commit: all participants hold locks until coordinator confirms. If coordinator crashes between "prepare" and "commit", locks are held indefinitely — the entire system freezes. Unusable across microservices.

    Saga Orchestration Flow
    Saga Orchestrator (Temporal) Step 1: createOrder() ← if fails: nothing to undo Step 2: reserveInventory() ← if fails: (nothing paid yet) Step 3: chargePayment() ← if fails: compensate step 2 Step 4: dispatchRider() ← if fails: compensate 3 + 2 Step 5: confirmDelivery() ← happy path complete
    Java: Compensating Transaction
    @WorkflowInterface public interface OrderSaga { @WorkflowMethod void processOrder(Order order); } // In workflow implementation (Temporal): @Override public void processOrder(Order order) { OrderActivities activities = Workflow.newActivityStub(...); String inventoryReservation = activities.reserveInventory(order); try { String paymentId = activities.chargePayment(order); try { activities.dispatchRider(order); } catch (ActivityFailure e) { activities.refundPayment(paymentId); // compensate activities.releaseInventory(inventoryReservation); // compensate throw e; } } catch (ActivityFailure e) { activities.releaseInventory(inventoryReservation); // compensate throw e; } }
    Secret: The Outbox Pattern is what makes Sagas reliable. Each local DB transaction also writes to an "outbox" table. A separate process reads the outbox and publishes to Kafka. This ensures events are published if-and-only-if the DB commit succeeds.
    Interview Trap: Designing choreography-based Saga for a 5-step order flow. Choreography scatters the business logic across 5 services — impossible to debug. Use orchestration (Temporal) for complex flows.

    Upload Client → Chunked S3 Multipart (5MB chunks) → Upload Complete Event → Kafka ("video-jobs") → Transcoding Workers (one per resolution): 360p worker → S3 output + DB status update 720p worker → S3 output + DB status update 1080p worker → S3 output + DB status update 4K worker → S3 output + DB status update → All done → CDN invalidation → Video Live

    Kafka Consumer Processes Same Event Twice
    Exactly-OnceOffset ManagementIdempotent ProducerManual Commit
    Architecture + Java Deep Dive
    Root Causes

    1. Auto-commit before processing: offset committed at 5-sec interval — crash mid-processing replays from committed offset. 2. Producer retries: producer doesn't get ACK (network blip) and resends — Kafka stores duplicate.

    Java: Manual Commit + Idempotent Consumer
    // Producer: idempotent (no duplicates from retries) props.put("enable.idempotence", "true"); props.put("acks", "all"); props.put("retries", Integer.MAX_VALUE); // Consumer: manual ack only after successful processing @KafkaListener( topics = "payments", containerFactory = "manualAckFactory") public void process(PaymentEvent event, Acknowledgment ack) { try { // Idempotent operation: upsert by event ID if (!processedEvents.contains(event.getId())) { paymentService.process(event); processedEvents.add(event.getId()); // Redis set } ack.acknowledge(); // ONLY after success } catch (Exception e) { // Don't ack — message will be redelivered log.error("Processing failed, will retry", e); } }
    Secret: Kafka's Exactly-Once Semantics (EOS) = enable.idempotence=true + transactional.id. But EOS only prevents duplicates within the Kafka → Kafka path (Kafka Streams). Writing to a DB still needs application-level idempotency check.
    Interview Trap: Saying "just use enable.idempotence=true and all duplicates are solved." EOS does NOT prevent duplicates when the final destination is a DB — that requires idempotent consumers at the application layer.

    Order Events Arrive Out of Sequence
    Kafka PartitionsEvent OrderingSequence NumbersReorder Buffer
    Architecture + Java Deep Dive
    Why Ordering Breaks

    Kafka guarantees order within a partition. With 10 partitions and round-robin assignment, events for Order #123 land on different partitions — consumed out of order. Same partition key = same partition = ordered.

    Fix: Partition by OrderId
    // Producer: always use orderId as key → same partition kafkaTemplate.send("order-events", order.getId().toString(), // KEY = orderId event); // Consumer: per-partition ordering is guaranteed // But: if you need global ordering across partitions, // use a reorder buffer with sequence numbers: Map<Long, TreeMap<Long, OrderEvent>> buffers = new ConcurrentHashMap<>(); public void process(OrderEvent event) { TreeMap<Long, OrderEvent> orderBuffer = buffers.computeIfAbsent(event.getOrderId(), k -> new TreeMap<>()); orderBuffer.put(event.getSequenceNo(), event); // Process consecutive events from buffer long expected = lastProcessed.getOrDefault(event.getOrderId(), 0L) + 1; while (orderBuffer.containsKey(expected)) { processEvent(orderBuffer.remove(expected++)); } }
    Secret: Producer-assigned sequence numbers are the key. Without sequence numbers, you can't detect gaps — you don't know if you received events 1, 3, 4 and are waiting for 2, or if 2 simply doesn't exist.
    Interview Trap: Using a single-partition topic to guarantee global ordering. A single partition = no parallelism = throughput bottleneck. Correct answer: partition by entity ID (orderId) and accept per-entity ordering.

    The JOIN Problem at Scale

    A JOIN across posts (1B rows) + users (500M rows) requires a hash join or nested loop — billions of comparisons even with indexes. At Instagram's read QPS (millions/sec), this is physically impossible. Denormalization stores the answer pre-computed.

    Denormalization Example
    Normalized (unusable at scale)Denormalized (Instagram)
    posts: id, author_id, content

    (author data duplicated in post row)
    When Does Denormalization Break

    Architecture + Java Deep Dive
    Why Hot Partitions Happen

    DynamoDB auto-shards by partition key. If all writes go to the same partition (e.g., userId = popular celebrity), that partition gets 100% of writes but is capped at 1000 WCU/sec. Result: throttling errors.

    Fix: Write Sharding
    // BAD: userId as partition key for high-traffic user PutItemRequest bad = PutItemRequest.builder() .tableName("posts") .item(Map.of("PK", attr("USER#virat"), "SK", attr(postId))) .build(); // GOOD: append shard suffix to partition key int shard = ThreadLocalRandom.current().nextInt(10); // 0-9 PutItemRequest good = PutItemRequest.builder() .tableName("posts") .item(Map.of("PK", attr("USER#virat#" + shard), "SK", attr(postId))) .build(); // Read: scatter-gather across all 10 shards List<GetItemRequest> shardReads = IntStream.range(0, 10) .mapToObj(s -> GetItemRequest.builder() .tableName("posts") .key(Map.of("PK", attr("USER#virat#" + s))) .build()) .toList(); // Execute in parallel, merge results
    Secret: The shard count (10) must be chosen based on expected max writes. Too few = still hot. Too many = scatter-gather reads hit all shards unnecessarily. Most production systems use 10-20 shards and tune based on metrics.
    Interview Trap: "Just increase RCU/WCU provisioned capacity." Higher capacity doesn't fix hot partitions — a single partition is still capped regardless of total table capacity. Must fix the partition key design.

    Cache StampedeTTL JitterMutex LockPER Algorithm
    Architecture + Java Deep Dive
    How a Stampede Happens
    Normal: User A reads → Cache hit → return data Stampede: T=0: Popular key expires (TTL hit) T=0.001: 10,000 concurrent requests → ALL get cache miss T=0.002: 10,000 threads all query the DB simultaneously → DB CPU spikes to 100% → query timeout → DB crash
    Three Defenses
    // 1. TTL Jitter — spread expiration across time window int ttl = BASE_TTL + ThreadLocalRandom.current().nextInt(JITTER_RANGE); redis.setex(key, ttl, value); // 2. Mutex Lock — first requester refreshes, others wait RLock lock = redisson.getLock("refresh:" + key); if (lock.tryLock(100, 5000, MILLISECONDS)) { try { String val = redis.get(key); if (val == null) { // double-check after acquiring lock val = db.fetchExpensiveData(key); redis.setex(key, TTL + jitter(), val); } return val; } finally { lock.unlock(); } } else { return redis.get(key); // another thread is refreshing — wait and retry } // 3. PER (Probabilistic Early Recomputation) — preemptive refresh // When remaining TTL < delta, probabilistically trigger refresh early long remainingTTL = redis.ttl(key); if (remainingTTL < DELTA && Math.random() < (1.0 / remainingTTL)) { asyncRefresh(key); // background refresh before expiry }
    Secret: The PER (Probabilistic Early Recomputation) algorithm is the most elegant solution — it avoids the stampede by probabilistically refreshing the cache before it expires, with no distributed lock needed.

    Why LLMs Hallucinate

    LLMs are next-token predictors trained to generate plausible text — not to retrieve facts. Without grounding, they generate what sounds correct. RAG (Retrieval-Augmented Generation) provides real documents as context so the model answers from evidence.

    RAG Pipeline Architecture
    Ingestion: Documents → Chunker (500 token chunks) → Embedding Model (text-embedding-3-small) → pgvector / Pinecone (store vectors) Query: User Query → Embed → Vector Similarity Search (Top-K=5) → Retrieved Chunks → Prompt: "Answer using ONLY this context:" → LLM (GPT-4o) → Answer with source citations
    Java: Spring AI RAG
    @Autowired VectorStore vectorStore; // pgvector backed @Autowired ChatClient chatClient; public String answerWithRAG(String userQuery) { // 1.
